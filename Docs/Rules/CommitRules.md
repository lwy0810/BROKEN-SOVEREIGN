# 커밋 메시지 규칙

커밋과 PR을 만들 때 따르는 규칙입니다. 규칙은 이 문서에만 적습니다.

## 형식

```
[Type] 요약
```

- 요약은 50자 이내로 쓰고 명사형으로 끝냅니다. 마침표를 찍지 않습니다.
- 커밋 하나에는 변경 하나만 담습니다. 기능 추가와 버그 수정을 한 커밋에 섞지 않습니다.
- GitHub 이슈를 고친 커밋은 본문에 `fixes #이슈번호`를 적습니다.

## Type

| Type | 쓰는 경우 | 예시 |
|---|---|---|
| `[Feat]` | 기능 추가 | `[Feat] 신앙 충만 상태 추가` |
| `[Fix]` | 버그 수정 | `[Fix] 신앙이 두 번 충전되는 문제 수정` |
| `[Refactor]` | 동작은 그대로 두고 코드 정리 | `[Refactor] 플레이어 이동 로직 분리` |
| `[Test]` | 테스트 추가·수정 | `[Test] 격 돌파 조건 테스트 추가` |
| `[Asset]` | 에셋 추가·교체 | `[Asset] 격광 강타 이펙트 교체` |
| `[Docs]` | 문서 수정 | `[Docs] 폴더 구조 규칙 갱신` |
| `[Chore]` | 설정·패키지 변경 | `[Chore] Input System 패키지 추가` |

## 브랜치

- `main` 브랜치에 직접 커밋하지 않습니다.
- 작업마다 브랜치를 만들고, 끝나면 `main`으로 PR을 올립니다.

| 작업 | 브랜치 이름 | 예시 |
|---|---|---|
| 기능 | `feature/<짧은-설명>` | `feature/click-move` |
| 버그 수정 | `fix/<짧은-설명>` | `fix/double-faith-gain` |
| 테스트 | `test/<짧은-설명>` | `test/breakthrough-condition` |
| 문서 | `docs/<짧은-설명>` | `docs/class-diagram` |

- PR 제목도 커밋 메시지와 같은 `[Type] 요약` 형식으로 씁니다.

## 이슈

- 이슈 제목은 `[Bug] 요약` 형식으로 쓰고, 요약 규칙은 커밋 메시지와 같습니다.
- 라벨은 `bug`와 심각도(`critical`, `high`, `medium`, `low`) 하나를 붙입니다.
- 본문에는 재현 절차, 기대 동작, 실제 동작, 관련 파일을 적습니다.

## 태그

- `Docs/GDD.md` 마일스톤의 주차 말 시점 `main`에 태그를 붙입니다. 발표 직전 문제가 생기면 이 시점으로 돌아가 빌드합니다.

| 태그 | 시점 |
|---|---|
| `v0.1-prototype` | 1주차 말 (전투 기반) |
| `v0.2-alpha` | 2주차 말 (성장 시스템) |
| `v1.0` | 3주차 말 (반신과 보스) |
